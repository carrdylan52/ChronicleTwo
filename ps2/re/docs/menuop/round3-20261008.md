### Storage hypotheses

Private coordinate-capacity diagnostics use the first pair exactly as the
observed integer references do. Nine pairs occupy 0x120..0x167: the first
pair is addressed, and the unused eight pairs account for the whole gap.
This reproduces every retail frame/local offset. Combined with the retained
register expressions, it yields zero masked word differences. Ten pairs,
following the shape of the manual/option item-coordinate arrays, place the
first scratch buffer at 0x170 instead of 0x168 and do not match the layout.

The nine-pair case is **not retained**. The global message-form array has nine
entries, but KeyStep repeatedly uses one coordinate pair and provides no
access establishing a nine-pair local array. Enlarging that scratch array
would reserve the desired bytes without independent evidence of its extent.
The diagnostic zero therefore is not a natural-source promotion or a solved
local type. It isolates the remaining problem to unused storage, rather
than another instruction, frame-alignment or register-allocation error.

The quest confirmation passes count `MES_VALUE_MAX` (16), while the observed
initializer and buffer writes cover two integers. Giving that actual buffer
16 uninitialized slots, then assigning its two observed values, produces a
0x1A0 frame but puts the buffer at 0x128 and changes the body to 0x1A54;
1087/1692 words differ. The larger count does not explain storage *before*
the buffer. No such edit is retained.

The real `SetMsgVolumeNoOne` definition remains out of line in the retained
caller. A visible non-inline definition leaves the frame at 0x160 and the
entry score at 28. Visible inline definitions under depth 1 or a dont_inline
setting retain the prior 0x1A0-frame/0x1B04-body result: their expanded calls
are different from retail. Depth 0 changes other inline calls, leaves a
0x160 frame, and emits a 0x1954 body. These are rejected caller-storage
explanations, not proposals to move or redeclare a message setter.

## Matching register expressions

`if (0 <= next || first_step != 0)` expresses the existing transition test
and emits retail's `slt at` at +0x12A8/+0x14B4 and `beqz at` at +0x14B8.
The entry spelling `(next < 0) == false` uses v0 at those three locations.
Using the literal on the left of this natural signed comparison resolves
all three operands without a boolean scratch value or changed control flow.

A genuine function-scope `transferred` local captures the current card
transfer count at the four progress updates. The saving case then calls
`StepMenuDl2(dl_base + transferred)`. This preserves retail's three loads
and restores `addu a0,v0,v1` at +0xABC. The direct member sum and the reversed
sum with this local emit `addu a0,v1,v0`. No extra instruction or live game
state is introduced. The close-page BGM load uses the existing typed
`SaveMenuStack.stGetTop()` accessor, preserving code while removing inherited
raw pointer arithmetic from this draft.
