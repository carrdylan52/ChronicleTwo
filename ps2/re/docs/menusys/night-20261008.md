- The four input integers are copied into `MENU_ITEM_MOVE_INFO::from` by a
  four-iteration loop over `table[i][j]`. MWCC unrolls it completely; the first
  iteration keeps its index-zero address as `addu a1,a0,$0` before `lh a1,0(a1)`,
  which is the retail "row-pointer copy". The same unrolled-first-iteration
  `addu rd,rs,$0` appears in the matched `GetCharaMemAllocSize` (charasetup)

  `slot` is already live fold the zero offset and lose the copy.
- The named row pointer `int *slot = table[i]` is declared after the copy loop.
  Removing it (indexing `table[i][k]` everywhere) makes MWCC strength-reduce
  `&table[i][1]`/`&table[i][3]` into extra pointer temporaries.
- The list test is `move->from[2] == 0`. With `!move->from[2]` MWCC keeps a
  `dsll32`/`dsra32` re-sign-extension before the later `== 1` test; with the
  explicit comparison the retail `nop` remains instead.

## CMenuItemInfo::LRCheck — promoted

`LRCheck__13CMenuItemInfoFi` matches (0/220, raw `0x370` = retail symbol
size 880) and the whole unit passes. The shoulder-button test is a `switch`
whose single case group (`MENU_SELECT_KEY_L1`, `R1`, `L2`, `R2`, in that
order) holds the page logic; any other key falls out of the switch to the
final `return 0`.

The two words at `+0x264/+0x268` were a delay-slot decision. MWCC's
delay-slot pass lets a conditional branch take the first instruction of its
target block (and retarget past it) only once per target: in the matched
retail code, no target is stolen from by two conditional branches. With the
`if (...) { return 0; }` key test, nothing else steals the final block's
`move v0,zero`, so the held-type rejection branch at `+0x264` takes it and
targets `+0x34C`. With the switch, the default exit is an unconditional jump
to that final block. It steals `move v0,zero` first (`b +0x34C` with the move
in its slot at `+0xB4/+0xB8`, which looks the same as an early return), so the
later rejection branch keeps retail's `nop` and targets `+0x348`.

- The switch with the cases written R2, L2, R1, L1 (the draft's comparison
  order) gives 4: MWCC emits the comparisons in the reverse of the written
  case order, so the cases are written L1, R1, L2, R2 to give retail's
  `0x80, 0x40, 0x20, 0x10` chain (`lr-sw1`, `lr-sw2`).
- The same rule explains the matched `CheckOmakeVtuto` (menuop): its second
  test steals the shared `return 0` and its fourth keeps a `nop`. Toy
  compiles in `.private/nm/ds/` (`t2`–`t6`) reproduce both outcomes from the
  same tail by changing only which earlier branch can steal.
