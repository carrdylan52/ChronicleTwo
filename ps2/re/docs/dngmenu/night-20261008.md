## Round 1 (nminv): DngTreeMapInit and ClsMes::Init promoted

Base `9a6519fc`, same image and settings. Receipts are under
`.private/nminv-r1/` (`probes/dngmenu/`, `receipts/`, `ledger.jsonl`).

`DngTreeMapInit__FP9mgCMemoryPiii` is now exact (0x3F8 bytes, GLOBAL, in
the 0x400 reservation). Two source corrections close its 55 words:

- **Opening modes are a switch.** Retail tests `li v0,3; beq s6,v0,sep;
  beqz s6,sep; b default`, an unoptimized two-target chain followed by an
  unconditional branch to the common-menu block. `if (mode == 3 || mode == 0)`
  inverts the last test (`bnez`), and every boolean form normalizes with
  xori/sltiu. `switch (menu_mode) { case 0: case 3: ... break; default: ... }`
  emits retail's chain exactly. MWCC compares the labels in reverse order:
  `case 3: case 0:` tests zero first. The values are `MenuOpenType`
  (`MENU_OPEN_MAIN_TOWN` from the world map, `MENU_OPEN_DNG_TREE_MAP` from
  the tree-map request; the in-dungeon main menu supplies its own type).
- **The cursor buffer is a byte image pointer.** Retail stores
  `MenuCursorDataBuff` and reloads it for `LoadFileMenu` because the global
  is not `u_long128 *`: storing a converted `stGetTop()` result and passing
  `(u_long128 *) MenuCursorDataBuff` produces the store/reload pair. Its only
  other consumer, `CMenuTreeMap::InitEnd`, passes it to
  `EnterIMGFile(u_char *)`, so `u8 *` removes that cast. `void *` and
  `char *` also match; `u8 *` is retained for the IMG consumer. The earlier
  byte/void-global probes (71 words) combined these types with the boolean
  condition; with the switch they are exact. An assignment inside the
  loader argument does not reload.

With the native tree initialization, the inline constructor emits
`Init__6ClsMesFv` (retail binding 13) from the unchanged shared header, so
its assembly marker is removed. The complete dngmenu object passes
(0x8BB0 bytes, 1,214 relocations), all 149 objects pass, and
`SCES_511.90: OK` (6,756 perfect).

## Round 1 (nminv): MsgInit probes

`MsgInit__12CMenuTreeMapFv` stays at **7/116**. New measurements:

| Form | Result |
|---|---|
| `y` declared at function top (alone, with `message`, with `i`) | 7 |
| `const int y` | 7 |
| `y` in its own block scope | 7 |
| Named X declared before `y` | 7 |
| X0 as `-(w0 >> 1) + (W >> 2)`, `(W >> 2) * 1`, `(W >> 1) >> 1` | 7 |
| `int x = W >> 2; x -= w0 >> 1;` | 8 (width now loads before line width) |
| Field compound `line_pos[0][0] -= ...` | 0x1D8 |
| `line_pos[1][1] = line_pos[0][1]` | 0x1D4 |
| `line_pos[0][1] = y = H - 50` | 8 |
| Early save-label store, extern or private static | 23 |
| dngmenu GPR helper mask 0, 0x8, 0x10, 0x20, 0x40, 0x70, 0xF0, 0x1F0, 0x3F0, 0xFFF0 | 7 (insensitive) |

Diagnostics show MWCC schedules the first-line X chain before the height
load whenever height feeds only Y: height loads first only when it also
feeds X (`(W >> 2) - (H >> 1)`), when Y is stored first, or when the save
label is stored first. Within the X expression native code always loads the
`message`-relative line width before the global width, unless the width is
a separately assigned local. Retail's order (height, width, line width)
therefore needs both a different X evaluation order and an earlier Y
dependency; no natural form found supplies the second.
