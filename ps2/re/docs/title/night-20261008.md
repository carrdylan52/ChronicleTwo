[selector-context-20261008.md](selector-context-20261008.md), now committed in

The memory-card snapshot keeps the card pointers and the inserted-port bytes
in two-element arrays, as the matched `TitleMCCheckKey` in this unit does
(`MC_CARD_INFO *cards[2]`, `u8 inserted[2]`):

```cpp
MC_CARD_INFO       *cards[2];
u8                  inport[2];
cards[0] = &card_manager->card[0];
cards[1] = &card_manager->card[1];
inport[0] = TitleMCCheckInport[0];
inport[1] = TitleMCCheckInport[1];
```

MWCC keeps the constant-indexed elements in registers, but colours them
differently from separate scalars: `inport[1]` takes `s1`, `inport[0]` `s2`,
`cards[0]` `s3` and `cards[1]` `s0`, with both narrowing `andi`s in place, as
in retail. The card pointers are assigned before the port bytes; all six
declaration orders of `card_manager`, `cards` and `inport` give 0 with that
assignment order and 6 with the ports assigned first (`tk-b*`). A port array
alone with scalar card pointers gives 13 (`tk-a3`: the ports flip but the
card pointers move to `s2`/`s3`).

The four two-argument fade calls pass their zero limit explicitly
(`CalcMenuAdd(&TitleInfo->menu_alpha, float(-12.0), 0.0f)`); the former
file-local redeclaration with a default argument is removed, and the function
uses the `menucommon.hpp` declaration. The explicit and default forms compile

### Earlier scalar-snapshot probes

With the rows the draft gives 5 words, all in the memory-card snapshot block.
Retail holds `inport0` in `s2` and `inport1` in `s1`; MWCC reverses them. The
snapshot reads both input-port bytes and both card pointers before the

New negative trials (trials `.private/nm/title/tk-*`, all with the rows):

- All 120 block-scope declaration orders of `card_manager`, `card0`, `card1`,
  `inport0` and `inport1` (`tk-p*`): best 5 (15 orders), otherwise 8, 9, 12
  or 13.
- The four snapshot locals declared at function entry, in all 24 orders
  either before (`tk-fr*`) or after (`tk-fo*`) the existing entry locals:
  best 5, otherwise 8, 9, 12 or 13.
- A two-byte `inport[2]` array: filled by a loop 561, aggregate-initialized
  614, two element assignments after the card pointers 13.
- Diagnostic only, not source candidates: an extra `!= 7` use of either port
  (507, 515) changes the block's schedule rather than only its colouring.
- All 23 other orders of the four snapshot assignments (`tk-as*`): the loads
  follow the written order, but `TitleMCCheckInport[0]` always lands in `s1`
  and `[1]` in `s2`. Orders that assign `inport1` first report 3 masked words
  only because the probe masks relocation addends; the loads then fetch the
  other element into each register, which the object check rejects.

Toy compiles (`.private/nm/ds/t7`–`t10`, neutral translation unit) reproduce
the native allocation exactly: `card1` `s0`, `inport0` `s1`, `inport1` `s2`,
`card0` `s3`, with the second port's `andi` written to `s1`. Integer
snapshots instead follow declaration order. Neither declaration order,
assignment order, a combined declaration, `==`/`else` or `!=` tests, a `bool`
lost flag, explicit `(int)` casts, a reordered flag assignment, nor snapshots
placed after the `TitleMCCheckNow` return (MWCC does not hoist them above that
branch) gives the second port the lower register. Changing use counts, range
lengths or test order moves both ports (`s2`/`s0`, `s0`/`s3` and similar), and
named call results move the `andi` after each call (`s4`/`s0`), so the choice
follows the ports' uses and live ranges rather than their declaration or
numbering. Retail's `inport1` `s1` / `inport0` `s2`
(both `andi` in place) therefore needs a different use structure that has not
been identified.

With scalar snapshots no form exchanges the two port registers without
disturbing the rest of the block. `TitleBootInit` was not attempted; it is the placement-new blocker
recorded in [notes.md](notes.md).

## Round 1b — retained TitleBootInit improvement

Continuation base `0c1685ff`, same image and canonical profile. The cancelled
round-1 run left its TitleBootInit sources and scores in
`.private/nmmenu-r1/title-src/` and `title/`; those probes are retained as
evidence and are not repeated. Existing m2c output is
`title-analysis/TitleBootInit.m2c.txt`.

The guarded draft improves from **56/676 to 30/676** without new SF rows:

- Declare the LOCAL TitleBootInit as `static`.
- Use signed `int` file-size outputs, matching LoadFile2's declaration, and
  a separate scoped logo size. Retail passes stack `+0x2DC` for that size
  and `+0x2D8` for subsequent loads; the prior shared local conflated them.
- Declare `map_no` before `map_buffer`, then acquire the buffer before
  SearchMapNo. This restores their saved-register allocation without
  changing the call order.
- Capture the remaining read-buffer capacity before its top pointer, then
  call stSetBuffer with those meaningful values. This restores the final
  buffer setup's instruction order.

Private full-wrapper confirmation `title/r1b-mapdecl-full/score.json`
reproduces **30/676**, body `0xA84` in padded extent `0xA90`; the whole-unit
native probe still fails only within TitleBootInit. Residual groups are
follow-camera float materialization (`+0xC0..+0xD4`), the map-buffer copy
(`+0x180/+0x188`), map-load option stores (`+0x2B4..+0x2C0`), icon-loop
registers and memcpy argument order (`+0x520..+0x590`), menu-resource setup
(`+0x730..+0x750`), and the previously documented placement-new branch
(`+0x7D8/+0x7DC`). The function remains guarded.
