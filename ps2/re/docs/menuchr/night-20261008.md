## EnterDataMenu match

`EnterDataMenu__15CMenuChrCngMenuFPUc` is native and byte-identical.
Retail's GLOBAL symbol is `0x608` bytes; the earlier `0x610` header size
was the padded comparison extent. The menuchr object passes the complete
checker (`0x11CBC` bytes, 3,766 relocations).

The party change palette (`palette.clut`, `0x1A80`) holds 256 colours of
one byte per channel. Retail reads and writes red, green and blue with
`lbu`/`sb` at offsets 0, 1 and 2 and advances one pointer by four bytes
per colour, so the palette and the global `MenuCharaChangeCLUT` are typed
as `CHR_CNG_CLUT_COLOR` (`r`, `g`, `b`, `a`). The loop walks that typed
array with `color++`. Initializing the palette index before the colour
pointer gives retail's `s2` index / `s3` pointer roles; the reverse order
exchanges them (22 words). The band search ends at
`step < CHR_CNG_CLUT_BAND_NUM + 1`: the equivalent `step <=
CHR_CNG_CLUT_BAND_NUM` compares into `at` instead of `v0` (2 words).

The remaining 11-word NPC command residual (index `a1`, stride `a2`
exchanged) is resolved by one function-scope `int i` shared by the party
loop, the command reset and the two command/cost loop pairs. A block-scope
index, alone or declared before `first_message`, keeps 11 words; reusing
that index for the palette loop as well gives 16. The pack-file names,
`INIT_FORM` and the part-name formats use the unit's existing retail
literal symbols (`at_1276__3` .. `at_1285__2`), as the other native
menuchr functions do while the unit's data is still assembly.
`MenuCharaChangePosDataCfgBuffer` holds the configuration file's address
and is typed `u_int *`; its zero test and the constructor's clear are
unchanged in the object. `GetPartyCharaInfo` already returns
`PARTY_CHARA_INFO *`, so the redundant cast is removed.
`CHR_CNG_NPC_COMMAND_NUM` sizes `npc_cmd_mes`.

Validation: the full build prints `SCES_511.90: OK`; check_objects passes
149/149. Building the previous and new sources in the same tree changes
only `build/pal/obj/menuchr.cpp.o` and `build/pal/objdiff/base/menuchr.cpp.o`.
Receipts are under `.private/nmchr-r1/` (`build-baseline.log`,
`build-enter2.log`, `objects-enter2.log`, `hashes-baseline.json`,
`hashes-enter2.json`, and the probe directories `en-*`, `ei-*`).

## Character-change star drawing (round 1)

`MenuCharaChangeStarDraw__Fv` matches byte-for-byte once `mgRect<short>`
is the generic `mgRect` template. That needs a shared-header change, so
the function stays guarded. The guarded draft is the final source, and
the header change is a proposal (below). Retail's GLOBAL symbol is
`0x5BC` bytes; `0x5C0` is the padded comparison extent.

Retail evidence for the generic template:

* `Set__9mgRect<s>Fssss` (`0x2C4240`, 20 bytes) is WEAK, as are the
  `int` and `float` instantiations. That is the binding of an implicit
  template instantiation. StarDraw calls it out of line; the draft's
  explicit `mgRect<short>` specialization defines `Set` inside the class,
  so it was inlined.
* Retail's frame is `0x110`. The star rectangle occupies a 16-byte-aligned
  slot at `sp+0xD0`, before the two circle rectangles (`0xE0`, `0xF0`), and
  the ring centre is at `sp+0x108`. Only a 16-byte-aligned rectangle (the
  generic template's `aligned(16)`) gives that frame. An 8-byte rectangle
  gives a `0x100` frame with the star rectangle at `sp+0xF8`.
* The 8-byte packed tables (`table_1650`, `item_transtbl`,
  `start_button_tbl_1826`) therefore cannot have the type `mgRect<short>`.
  `MENU_SHORT_RECT` in menudraw.hpp now types the two menudraw tables;
  `title.cpp` includes that header.

Source findings, each measured on the out-of-line, 16-byte-aligned
rectangle (words / 368):

| Cumulative change | Words |
| --- | ---: |
| Out-of-line short `Set` (8-byte rectangle, earlier draft) | 289, body `0x5CC` |
| `tex_manager` local for both reloads (retail `s0`), aggregate `center`/UV initializers, direct sparkle indexing | 319, body `0x5CC` |
| + 16-byte-aligned star rectangle (frame `0x110`) | 315, body `0x5CC` |
| + corner values computed before the UV aggregate | 228, body `0x5CC` |
| + circle rectangles passed as argument temporaries | 228, body `0x5CC` |
| + absolute pulse as a conditional expression | 78 |
| + corner values declared `u1`, `v1`, `u0`, `v0` | 55 |
| + `0.0f < alpha` sparkle test | 53 |
| + circle-phase floats declared `circle`, `alpha`, `wave`, `pulse_alpha`, `y`, `x` | 37 |
| + ring radius as a second assignment of `size` | 34 |
| + `center[0] + x` written inside both rectangles | 15 |
| + one `int i` declared after `prim`, shared by the fan, circle and sparkle loops | **0** |

Details:

* `center` and the corner UVs are aggregate initializers. MWCC copies a
  zero template (`at_2371__4` in `.sbss`, `at_2372__4` in `.bss`) and then
  stores the computed elements. The build repoints the compiler's own
  template copies at those placeholders, so no data migration is needed.
  The `RingCenter` and `QuadTexCoords` stand-ins are removed.
* Named `inner`/`outer` rectangles take frame slots before the star
  rectangle. Constructing them as `DrawWakuCircle` argument temporaries
  places them after it, as retail does.
* `if (pulse < 0) pulse = -pulse;` before the multiply schedules the
  `0.5f * star_alpha` load after the branch. The conditional expression
  evaluates it first, and it fills the branch delay slot.
* The four corner locals must be declared `u1`, `v1`, `u0`, `v0`. That
  order converts left, left+width, top+height and then top, as retail
  stores them; the other 23 orders give 67-302 words or a different body.
* MWCC colours declared locals in declaration order and compiler
  temporaries and reused-variable webs afterwards. Retail's
  `circle f21, alpha f22, wave f23, pulse_alpha f24, y f25`, then the cached
  `center[1]` `f26`, `x` `f27` and the radius `f28`, require the radius to be
  a second web of `size` and `center[0] + x` to be a common subexpression
  rather than a reassignment of `x`.
* Sparkle loop: retail colours the index last (`s4`, stride `s0`). A
  function-scope `int i` reused by the circle loop (or by all three loops)
  does this. Declaring it before `prim` swaps `prim` and the index (31 words).
* Negative, on the final source: `float angle = menu->star_angle;` at its
  declaration (11 words) or after `center` (20). Earlier steps: sharing `x`
  with the fan loop (34, unchanged), `x += center[0]` (34), the radius as a
  second assignment of `offset` (34), and a sparkle index declared at
  function scope but used only by that loop (53, unchanged).

With the current header the guarded draft compiles to 100/368 words,
because the 8-byte specialization still inlines `Set`. Building it in
the tree changes no object: SCES_511.90 OK, 149/149
(`.private/nmchr-r1/build-own1.log`, `objects-own1.log`,
`hashes-own1.json`). The probe sequence is under
`.private/nmchr-r1/probes/star-*`, `st*-*` and `stc-*`.

## Costume drawing match (round 1)

`Draw__15CMenuCostumeSelFv` is native and byte-identical (retail GLOBAL
`0x8D4` bytes). Two changes complete it.

1. The line pulse's magnitude is taken with a conditional expression,
   `wave = wave < 0.0f ? -wave : wave;`. With the statement form
   `if (wave < 0.0f) wave = -wave;` the merge `nop` and the right-origin
   conversion order at `+0x2AC..+0x2D8` still differ (64 words, production
   profile); the conditional expression resolves them (53 words). The same
   change resolved the pulse branch in `MenuCharaChangeStarDraw`. Other
   spellings: `0.0f > wave ? -wave : wave` 55, `6.0f * (|sin|)` 79,
   `wave >= 0.0f ? wave : -wave` 394.
2. The other 53 words all come from the help box: retail materializes the
   `36.0f` X argument (`lui 0x4210` at `+0x804`) before the
   `mgScreenHeight - 40.0f - 8.0f` Y argument. That is the floating
   argument evaluate-first state described in `docs/MWCC.md`. A scoped row
   selects it: `menuchr.cpp`, `Draw__15CMenuCostumeSelFv`, binary32
   `0x42100000`, callee `DrawMenuFillBox__Fffffiiii`,
   `expected_matches: 1`, `evaluate_first: true`. Source spellings tried
   without the row: integer `36` (53), integers `36` and `32` (53),
   `40.0f - 4.0f` (53), named X/Y locals (53),
   `(float) (mgScreenHeight - 40) - 8.0f` (53), and
   `mgScreenHeight - (40.0f + 8.0f)` (49; it folds to one `48.0f`
   subtraction where retail has two).

Probes: `.private/nmchr-r1/probes/cs3-*`, `cs4-*` and

## Temporary-scene initializer match (round 1)

`MenuItemCharaDataLoadEndCheckAfter` matches and is unguarded. It needs
two source features:

- The early return for load mode 2 is a `switch` with a single
  `case 2:` rather than an `if`. Both compile the same comparison and
  branch (`+0x5C`..`+0x68`). With the `switch`, MWCC leaves the message
  loop's back-branch delay slot empty and sets the `CMdsListSet` address
  in the `Initialize` call's slot (`+0xF4`/`+0xFC`), as retail does.
- The function is compiled under `#pragma inline_depth(8)`. At the
  default depth, the game-object array's constructor chain
  (`CScene` → `CSceneGameObj` → `CSceneCharacter` → `CSceneData`) stops
  one level short. The draft then calls an out-of-line WEAK
  `__ct__10CSceneDataFv` at `+0x190`, where retail calls
  `Initialize__10CSceneDataFv` directly. The extra constructor is also
  emitted as an unnamed `.text` piece. The function word comparison masks
  relocation targets, so every earlier "2/220" draft carried this third
  difference. Only `check_objects` reports it, as an unexpected piece after
  this function and unresolved jump-table targets.

| Variant (whole-object `check_objects`) | Result |
| --- | --- |
| `switch`, default depth | unexpected `__ct__10CSceneDataFv` piece |
| `if`, depth 5 or 8 | bytes differ at `+0xF4` |
| `switch`, depth 4, 5 or 8 | **pass** |

The source uses depth 8, as three of menuchr's other scoped blocks do. Wrapping
the scene phase in a block or declaring the character pointer before the
scene leaves 2 words (`probes/le2-*`, spec `v_le2.py`). Whole-object
probes: `.private/nmchr-r1/game/le3-*`.
